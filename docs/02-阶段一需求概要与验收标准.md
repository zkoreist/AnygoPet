# 阶段一需求概要与验收标准

> 版本：v1.0 ｜ 日期：2026-09-18 ｜ 状态：待评审

## 1. 背景与目标

做一个 Bongo Cat 形态的桌面宠物：常驻桌面的小型动画角色，透明无边框置顶窗口，可拖拽，点击有反应。

**阶段一的核心目标只有一个：验证「透明窗口 + 动画渲染 + 拖拽交互」这套骨架能跑通。**

键位映射、换肤、照片转桌宠都不是本阶段的目标。本阶段成功与否，不看功能多少，看桌面上是不是有一只"活着"的、能被拖着走的小家伙。

## 2. 用户故事

| 编号 | 作为…… | 我希望…… | 以便…… |
|---|---|---|---|
| US-1 | 用户 | 一开机就能在桌面上看到一只会动的小角色 | 桌面不那么冷清 |
| US-2 | 用户 | 能用鼠标把它拖到任意位置 | 它不挡住我正在用的窗口 |
| US-3 | 用户 | 点它一下它有反应 | 感觉它是活的 |
| US-4 | 用户 | 能从托盘或右键菜单关掉它 | 不想用时能彻底退掉 |
| US-5 | 用户 | 在 125%/150% 缩放的屏幕上它依然清晰 | 不用为了它改系统缩放 |

## 3. 功能需求

> 需求描述遵循 EARS 原则：Ubiquitous（始终满足）/ Event-driven（事件触发）/ Unwanted（异常处理）/ State-driven（状态中）/ Optional（可选）

### FR-01 窗口形态

- **Ubiquitous**：系统须以无边框、透明背景、始终置顶的窗口呈现角色。
- **Ubiquitous**：系统须使窗口不在任务栏中出现。
- **Ubiquitous**：系统须使点击角色透明区域时，鼠标事件穿透到下层窗口。

### FR-02 待机动画

- **State-driven**：处于待机状态时，系统须循环播放呼吸与眨眼动画。
- **Ubiquitous**：系统须将动画帧率上限限制为 30 FPS。
- **State-driven**：窗口不可见或被完全遮挡时，系统须暂停渲染。

### FR-03 拖拽

- **Event-driven**：当用户在角色上按下并移动鼠标时，系统须使角色跟随鼠标移动。
- **Event-driven**：当用户释放鼠标时，系统须持久化记录角色当前的屏幕坐标。
- **Unwanted**：若角色被拖出当前显示器可视区域，则系统须将其拉回可视区域边缘。

### FR-04 点击交互

- **Event-driven**：当用户点击角色时，系统须播放一次反馈动画。
- **Optional**：若用户短时间内连续点击多次，则系统可播放一次特殊反馈动画。

### FR-05 右键菜单与系统托盘

- **Event-driven**：当用户在角色上点击右键时，系统须显示上下文菜单，至少包含"置顶开关"与"退出"。
- **Ubiquitous**：系统须在系统托盘显示图标，并提供退出入口。
- **Optional**：若用户在设置中开启开机自启，则系统须随系统启动自动运行。
- **Ubiquitous**：系统须保证同时只有一个实例运行。

### FR-06 外观包

- **Ubiquitous**：系统须从外观包目录加载角色模型（**Live2D 格式：`.model3.json` + `.moc3` + 贴图**，及配套的按键 / 桌面背景 PNG）。
- **Event-driven**：当用户切换外观包时，系统须在不重启应用的前提下完成替换。
- **Ubiquitous**：系统自带的默认外观包须为可合法再分发的原创或 CC0 素材。

### FR-07 高 DPI 适配

- **Ubiquitous**：系统在 100% / 125% / 150% 缩放下，须保持渲染清晰且拖拽坐标准确。

### FR-08 多显示器

- **Ubiquitous**：系统须记录并在启动时恢复角色上次所在的显示器与坐标。
- **Unwanted**：若启动时目标显示器不存在，则系统须回退到主显示器居中显示。

## 4. 非功能需求

| 项 | 指标 |
|---|---|
| 常驻内存 | ≤ 120MB |
| 冷启动时间 | ≤ 2 秒 |
| 渲染帧率 | 待机 30 FPS，交互时 ≤ 60 FPS |
| 安装包体积 | ≤ 30MB |
| 支持系统 | Windows 10/11（项目本身跨平台，不主动裁剪） |
| 隐私 | 不联网、不收集任何用户数据 |

## 5. 明确不做（Out of Scope）

以下几项不是遗漏，是**有意推迟**：

- ❌ 键位映射 / 鼠标映射 / 手柄映射 —— 阶段二
- ❌ 自主行为（跟随鼠标、自己走动、无人时睡觉）—— 阶段二
- ❌ 照片上传与抠图 —— 阶段三
- ❌ 语音、聊天、联网能力
- ❌ 皮肤商店、社区分享

理由：自主行为需要引入行为状态机，会让状态管理复杂度翻几倍，但对"验证骨架"零贡献。

## 6. 验收标准

阶段一完成的定义（逐条打勾）：

- [ ] 双击启动后 2 秒内，角色出现在桌面上并开始待机动画
- [ ] 窗口无边框、背景透明、始终置顶、任务栏不可见
- [ ] 点击角色外的透明区域，鼠标事件能穿透到下层窗口
- [ ] 可用鼠标将角色拖到屏幕任意位置，松开后位置被记住
- [ ] 重启应用后，角色出现在上次的位置
- [ ] 将角色拖出屏幕边缘后，会被自动拉回
- [ ] 单击角色有明确的动画反馈
- [ ] 右键菜单可切换置顶、可退出
- [ ] 托盘图标存在且可退出
- [ ] 在 150% 缩放的屏幕上，角色边缘清晰、拖动手感准确
- [ ] 接双显示器时，角色能停在副屏并记住位置
- [ ] 常驻内存 ≤ 120MB
- [ ] 仓库中不含 Bongo Cat 原始美术素材
- [ ] 默认外观包为 CC0 或原创素材，授权声明齐全

## 7. 阶段二 / 三的预留说明

以下内容**现在不做，但架构上不要堵死**：

| 后续能力 | 现在的预留动作 |
|---|---|
| 键位映射 | 系统层预留全局钩子接口；第一阶段不启用 |
| 换肤 | 外观包采用「目录 + config.json」结构，换肤即换包，不做硬编码 |
| 照片转桌宠 | **已确认走 Live2D 路线**（2026-09-18 决策：先沿用、以后再改）。去背照片无法直接变成 Live2D 模型，阶段三需单独定档 |
| 多角色 | 外观包管理器按"多个包"设计，而非"一个角色" |

> ⚠️ **更正（2026-09-18）**：早期文档写的是"部件式序列帧"，与实际仓库不符，实际是 **Live2D（`.moc3`）**。
>
> 因此"照片转桌宠"在 Live2D 架构下门槛更高——**抠图容易，难的是让静态图动起来**。三条路径：
> 1. 纸片人式整体摇摆 —— 最省，效果一般，适合先跑通
> 2. 绑骨做成 Live2D —— 效果最好，需 Cubism Editor，新手 10–40 小时
> 3. AI 图生视频转帧 —— 办公本无独显跑不动，需云端
>
> **建议阶段二开工前先定档**，避免做完再返工。
