# 开发环境搭建与换机迁移手册

> 版本：v1.0 ｜ 日期：2026-09-18

## 1. 换机结论

**能换，而且是这个项目最不用担心的环节之一。**

这个项目换机的成本，几乎全部集中在"重装开发环境"，而不是"搬运项目"。只要满足三个前提：

1. 代码托管在 GitHub（fork 之后天然满足）
2. 依赖版本锁文件提交进了仓库
3. 美术素材不散落在本地临时目录

满足这三条后，换到任何一台 Windows 机器上重建项目，大约 1 小时（其中大部分是下载等待）。

## 5. 现在就该做的三件事（锁定版本）

换机体验是现在决定的，不是换机那天决定的。请立刻补上：

### 5.1 根目录加 `.nvmrc`

```
24
```

> 2026-09-19 核对：实际环境是 Node **24.15.0**，已对齐。
> 真正的硬性下限来自 pnpm 11+，它要求 **Node ≥ 22**。

### 5.2 `src-tauri/` 下加 `rust-toolchain.toml`

```toml
[toolchain]
channel = "stable"
```

> **刻意不写死 `stable-x86_64-pc-windows-msvc`**：Windows 上确实必须用 msvc 目标（不能用 gnu），
> 但写死 triple 会让 macOS / Linux 的贡献者加载不了这个文件。
> Windows 侧的正确性用 `rustup show` 确认，详见 7.6。

### 5.3 确认锁文件已提交

```bash
git ls-files | grep -E 'pnpm-lock.yaml|Cargo.lock'
```

两个文件都必须出现在输出里。若被 `.gitignore` 排除，需要改忽略规则。

## 6. 新机从零搭建步骤

**顺序是关键：MSVC 必须排在 Rust 前面**（原因见 7.6）。Node 与 pnpm 可以随时装。

```bash
# 1. 【最慢的一步，先启动】装 MSVC 生成工具
#    下载：https://aka.ms/vs/17/release/vs_BuildTools.exe      （VS2022，已验证够用）
#          或 https://aka.ms/vs/stable/vs_BuildTools.exe        （最新版，对应 VS2026 / v145）
#    详细组件清单见第 7.6 节。约 6-8GB，是唯一的硬门槛，优先验证。

# 2. 装 Rust（rustup 官网），装完重开终端让 PATH 生效
rustc --version
rustup show        # 默认工具链必须是 x86_64-pc-windows-msvc，出现 -gnu 就按 7.6 纠正

# 3. 装 Node.js 24 LTS（官网安装程序，勾选 "Add to PATH"）
#    装完重开终端，确认 node / npm 都能敲出来
node -v
npm -v
npm i -g pnpm
pnpm -v

# 4. 拉代码
git clone https://github.com/zkoreist/AnygoPet.git
cd AnygoPet

# 5. 安装依赖（注意：必须用 pnpm，npm / yarn 会被 preinstall 拦截）
pnpm install
#    若报 ERR_PNPM_IGNORED_BUILDS，说明 allowBuilds 没配好，见 7.7

# 6. 启动
pnpm tauri dev
```

验收：桌面出现透明窗口（位置可能不明显，**看托盘图标更可靠**）、角色会动、可用键盘/鼠标驱动。

> 首次 `pnpm tauri dev` 需要完整编译 Rust 二进制（含链接），比 `cargo check` 慢很多，
> 机器性能一般时可能十几分钟。日志持续滚动即为正常，不要以为卡死。

## 7. 已知坑

### 7.1 必须用 pnpm

项目 `package.json` 里有：

```json
{ "preinstall": "npx only-allow pnpm" }
```

**用 `npm install` 或 `yarn` 会直接失败**，这不是报错，是项目主动拦截。

### 7.2 MSVC 必须勾对组件

只装 VS Code 或只装 .NET 工作负载都不行，**必须勾选「C++ 桌面开发工作负载」**。磁盘占用约 5GB，提前确认空间。

### 7.3 Rust 装完要重开终端

`rustc --version` 若提示找不到命令，先重开终端再试，别急着重装。

### 7.4 渲染依赖 WebGL

PixiJS 8 跑在 WebGL 上。在**远程桌面、虚拟机、或禁用了硬件加速的环境**里可能黑屏或不渲染。验证渲染效果请务必在真机上做。

### 7.5 素材与大模型别硬塞进 git

序列帧素材和模型文件体积容易失控。建议：

- 小体积素材（单包 < 10MB）：直接进 git
- 大体积或二进制：用 Git LFS，或放网盘并在 README 里写明下载地址
- **无论哪种，都要确保换机时能拿到**

### 7.6 MSVC 生成工具安装详解

**下载**：https://aka.ms/vs/stable/vs_BuildTools.exe
（官方页面：https://visualstudio.microsoft.com/zh-hans/visual-cpp-build-tools/ ）
这是"仅生成工具"包，不含 IDE，比装完整 Visual Studio 小很多。当前对应 **Visual Studio 2026** 系列。

**安装时勾选**：

- 工作负载页：勾选 **「使用 C++ 的桌面开发」**
- 右侧"安装详细信息"确认包含：
  - **MSVC v145 C++ x64/x86 生成工具**（VS2022 是 v143，2026 是 v145）
  - **Windows 11 SDK**
  - **C++ CMake tools for Windows**（建议勾，部分依赖会用到）
  - Visual Studio C++ 核心功能
- **不要勾**：ATL / MFC、Clang 工具集、Spectre 缓解库——都会显著增大体积且本项目用不上

**磁盘**：工作负载本体约 6–8GB。注意**即使把安装目录改到 D 盘，安装程序缓存仍会占用 C 盘数 GB**，C 盘太紧会直接失败。

**装完验证**：

1. 重启一次（至少重开终端，否则环境变量没生效）
2. 开始菜单打开 **Developer PowerShell for VS 2026**，执行 `cl` —— 应输出编译器版本，而不是"无法识别"
3. 普通终端执行 `rustc --version` 正常即可

**一个容易踩的坑：Rust 必须用 MSVC 工具链，不能用 GNU。**

```bash
rustup show
```

默认工具链应为 `x86_64-pc-windows-msvc`。如果显示 `...-windows-gnu`，说明 rustup 装错了，执行：

```bash
rustup default stable-x86_64-pc-windows-msvc
```

（这条也解释了为什么必须先装 MSVC 再装 / 重装 Rust——rustup 会依据已有的工具链做默认选择。）

### 7.7 pnpm v11+ 会拦截依赖的构建脚本（2026-09-19 新增）

**这是换机后最容易踩、且报错信息极具误导性的一个坑。**

pnpm 从 v11 起，依赖的 postinstall 构建脚本**默认被拦截**（`strictDepBuilds` 默认 `true`），
未审核的脚本会让安装**以非零码退出**：

```
Error: ERR_PNPM_IGNORED_BUILDS
  × installing dependencies
  ╰─▶ Ignored build scripts: @parcel/watcher@2.5.6, esbuild@0.25.12, esbuild@0.27.7, simple-git-hooks@2.13.1
```

**注意：此时依赖其实已经装好了**，只是退出码是 1。若脚本链里有 `&&`，
后续命令会被这个非零码打断，看起来像"安装失败"，实际不是。

**处理**：在仓库根目录的 `pnpm-workspace.yaml` 里配置 `allowBuilds` 白名单
（本项目已配好，内容如下，**这个文件不能删**）：

```yaml
allowBuilds:
  esbuild: true # vite 依赖的原生二进制
  '@parcel/watcher': true # 文件监听原生模块（dev 热更新用）
  simple-git-hooks: true # 安装 git hooks
```

**另一个必须知道的连带变化**：从 pnpm v11 起，pnpm 专属配置**不再从 `.npmrc` 读取**，
必须写在 `pnpm-workspace.yaml` 里。老的 `onlyBuiltDependencies` / `neverBuiltDependencies`
等字段也已被 `allowBuilds` 取代。

> 附带一条识别经验：pnpm 检测到被拦截的脚本时，会**自动生成** `pnpm-workspace.yaml`，
> 但里面只写占位值 `set this to true or false`。看到这种占位内容说明它还没被填过。

### 7.8 Node 装在非标准路径导致 PATH 里没有它（2026-09-19 新增）

如果 Node 不是用官方 MSI 装到默认位置，而是装到了自定义目录（本项目所在机器是
`D:\Dev\apps\dev\nodejs`），**安装程序可能不会（或没能）把它写进 PATH**，表现为：

```
C:\Users\Administrator> npm -v
'npm' 不是内部或外部命令，也不是可运行的程序或批处理文件。
```

紧接着 `pnpm`、`npx` 乃至之前用它装的全局命令（如 `codex`）全部失效。

**排查**：`node.exe` 到底在哪

```bash
where node          # 若报"找不到"，说明 PATH 里确实没有
```

或直接在磁盘上找：`dir /s /b D:\node.exe`

**处理**：把这两条加进**用户级 Path**（系统属性 → 环境变量 → 用户变量 → Path）：

```
<你的 Node 安装目录>             例如 D:\Dev\apps\dev\nodejs
%APPDATA%\npm                    npm 全局命令目录，不加上 pnpm 就敲不出来
```

**改完必须重开终端**，PATH 是进程启动时读取的。验证：

```bash
node -v
npm -v
```

> 注意 `%APPDATA%\npm` 这一条常被漏掉——`node` 能用了不等于 `pnpm` 能用，
> 因为 pnpm 是装在 npm 的全局目录里的。

### 9.2 踩过的坑（换机后大概率重演）

**坑 1：git 被代理挡死**

`.gitconfig` 里有 `http.https://github.com.proxy = http://127.0.0.1:7890`，Windows 环境变量里还有 `http_proxy = 127.0.0.1:54333`。代理软件没开时，所有 git 操作都报
`Failed to connect to github.com port 443 via 127.0.0.1`。

- 处理：删掉 `.gitconfig` 里那一行；用 git 之前先把代理软件打开
- **排查提醒**：别只查 `git config --global --get http.proxy`，它对 URL 变体（`http.https://github.com.proxy`）无效，直接 `git config --list --show-origin` 全量看
- **网络实情**：这台机器直连 github.com 会被重置，必须走代理，而代理时好时坏 —— git 失败先怀疑代理

**坑 2：pnpm 缓存不完整 → 缺原生模块**

项目装在 D 盘时，pnpm 默认把缓存放在 `D:\.pnpm-store`。若写入失败会留下**不完整缓存**，下次重装复用它就会缺东西，表现为：

```
Cannot find module '@rollup/rollup-win32-x64-msvc'
```

- 处理：`node_modules` 和 `D:\.pnpm-store` **必须一起删**再重装，只删 node_modules 没用
- 若缓存目录权限不足，可显式指定：`pnpm install --store-dir C:\Users\<用户名>\.pnpm-store`

**坑 3：首次编译没那么慢**

实测 `pnpm tauri dev` 首次编译约 **56 秒**（此前文档估的 10–30 分钟过于保守）。

**坑 4：源码包没有 git 历史**

如果用 GitHub 的 tarball（源码压缩包）而不是 `git clone` 拉代码，目录里没有 `.git`，需要：

```bash
git init -b master
git remote add origin https://github.com/zkoreist/AnygoPet.git
git fetch origin
git reset --hard origin/master
```

若 fetch 后分支引用没落盘（遇到过），可用提交号直接接：
`git reset --hard <提交号>`

### 10.2 与第一台相反的一条：这台机器**不需要代理**

第一台的结论是"直连 github.com 会被重置，必须走代理"。第二台**完全相反**：

- `.gitconfig` 里残留着 `socks5://127.0.0.1:7890`（环境变量里还是另一个端口 7954，两处对不上），
  代理软件没开，导致 `git ls-remote` 报 `Failed to connect to github.com port 443 via 127.0.0.1`
- **但删掉这两行后直连一次就通**，TCP 443 与 api.github.com 都实测通过

**结论：同一个报错，两台机器的处理相反——一台要开代理，一台要删代理配置。**
遇到 git 连不上，先用 `git config --list --show-origin` 看清现状，再决定是加还是删，别照搬结论。

### 10.3 这台机器新踩的两个坑

**坑 A：pnpm v11+ 拦截构建脚本** → 详见 7.7。
报错是 `ERR_PNPM_IGNORED_BUILDS`，且依赖其实已装好，只是退出码非零。

**坑 B：Node 装在非标准路径，不在 PATH 上** → 详见 7.8。
`node` / `npm` / `pnpm` / `codex` 全部"不是内部或外部命令"。修复是把
`D:\Dev\apps\dev\nodejs` 与 `%APPDATA%\npm` 加进用户级 Path。

### 10.4 这台机器的其他实测数据（可作换机参考）

| 项目                                   | 实测                                                  |
| -------------------------------------- | ----------------------------------------------------- |
| `pnpm install`（首次，全新 store）     | 约 4 分钟                                             |
| `pnpm build:vite`                      | 约 11 秒（4406 模块）                                 |
| `cargo check`（首次，约 500 个 crate） | 约 5 分钟                                             |
